# Registro de decisões do workspace

Decisões que valem para todos os mods TC. As de cada mod ficam no `docs/DECISOES.md` dele.

| Data | Decisão | Motivo | Alternativas descartadas |
|---|---|---|---|
| 2026-09-29 | Workspace (hoje `TCMineMods`) com um repositório git e build Gradle multiprojeto (`core/`, `colony-bridge/`, próximos mods) | Core e mods mudam juntos: uma mudança no core já é compilada e testada contra todos com um `./gradlew build`; histórico do Colony Bridge preservado (`git mv`) | Um repositório por mod + core publicado num Maven (atrito a cada mudança no core); tudo num mod só |
| 2026-09-29 | TC Core como **mod separado** (o jogador instala o jar do core), declarado como dependência no `mods.toml` de cada mod | Escolha do autor; um core só no modpack, mesmo com vários mods TC | Jar-in-jar (core embutido em cada mod) |
| 2026-09-29 | ~~Configuração repetida de mod em `gradle/tc-mod.gradle`~~ (substituída em 2026-10-20 pelo plugin `tc.mod`) (NeoForge, parchment, `mods.toml`, testes) e versões comuns no `gradle.properties` da raiz | Mod novo = `build.gradle` de 1–2 linhas + `gradle.properties` próprio; versões de NeoForge/Minecraft mudam num lugar só | Copiar o `build.gradle` inteiro em cada mod |
| 2026-09-29 | Primeira leva do core: design system das telas, ghost slots, `RedstoneMode`, `MetricRing`/`MetricSeries` (tamanho da janela por parâmetro). Monitores ficam no Colony Bridge por enquanto | Só o que não depende de mod externo e que o mod de reatores vai usar; monitores exigem separar dados de desenho, melhor feito com o segundo mod em mãos | Mover os monitores já (grande, sem um segundo uso concreto para guiar o desenho) |
| 2026-09-29 | Mods agrupados em `mods/<nome>/`; nome do projeto Gradle continua curto (`:core`, `:colony-bridge`) via `projectDir` no `settings.gradle` | Raiz limpa com vários mods planejados; comandos (`./gradlew :colony-bridge:runClient`) não mudam | Tudo num único `src/` separado por pacote (perde o isolamento do compilador: core poderia importar um mod, jars montados com filtros frágeis); manter os mods soltos na raiz |
| 2026-10-06 | Altura da grade dos terminais TC numa **config de cliente do core** (`tccore-client.toml`, `GridHeight`: 5/8/janela toda, padrão 5), trocada por um botão da barra lateral e comum a todos os terminais | Pedido do autor (começar com 5 linhas e alternar como o AE2); preferência é do jogador, não do servidor, e salva sobrevive a reiniciar o jogo | Variável estática por tela (perde ao fechar o jogo); config de servidor (sincronizaria a preferência de um para todos); altura automática pela janela (comportamento anterior, sem escolha) |
| 2026-09-29 | Saída do build na raiz: intermediários em `build/<mod>/`, jars finais de todos os mods em `build/libs/` (em `build.gradle` da raiz) | Um lugar só para pegar os jars e instalar no ATM10; pastas dos mods só com código | Manter `build/` em cada mod e só copiar os jars para uma pasta comum (duas cópias do mesmo jar) |
| 2026-10-20 | Repositório renomeado para **`TCMineMods`** (padrão da marca TCMine); ids de mod e pacotes `org.tinycore.*` mantidos | Nome alinhado com o resto do ecossistema; o GitHub redireciona o endereço antigo | Trocar também os ids (`tcmine_core`...): apagaria os blocos dos mundos existentes |
| 2026-10-20 | Configuração comum dos mods num **plugin de convenção** `tc.mod` em `build-logic/` (substitui `gradle/tc-mod.gradle`); runs, dependência do TC Core e `localRuntime` passam para o plugin | Padrão do Gradle; o IntelliJ entende o plugin (o `apply from` aparecia em vermelho); três mods tinham os runs copiados | Manter o `apply from` (IDE sem ajuda, duplicação); Kotlin DSL (reescrever todos os builds de uma vez, sem ganho de função) |
| 2026-10-20 | Jars do ATM10 numa pasta **`libs/` na raiz**, comum a todos os mods | O Cloud Storage lia os jars da pasta do Colony Bridge (um mod dependendo da pasta de outro) | Uma `libs/` por mod (jars repetidos) |
| 2026-10-20 | Licença **GPL-3.0** em todos os mods (arquivo `LICENSE`), a mesma do TCMine | Escolha do autor; padrão do ecossistema | MIT (declarada antes nos mods.toml, sem arquivo de licença) |
| 2026-10-20 | Estilo do código no **`.editorconfig`** (com as chaves `ij_*` do IntelliJ) e formatar ao salvar no IDE; VS Code removido do repositório | Um arquivo versionado define o formato para qualquer máquina; as regras seguem o estilo atual (sem `import *`, sem quebrar linhas sozinho, Javadoc intocado) para não reescrever arquivos inteiros | Spotless no Gradle (mais uma dependência e um commit gigante de reformatação); estilo do IntelliJ salvo em `.idea/` (pasta de máquina, fora do git) |
| 2026-10-20 | Plano de cada mod em `mods/<mod>/docs/PLANO.md` (antes em `docs/planos/` da raiz) | Tudo de um mod numa pasta só; a raiz fica com o que é do workspace | Manter os planos na raiz |
| 2026-10-20 | Java do Gradle fixado em **21** (`gradle/gradle-daemon-jvm.properties`) | Com o Java 27 da máquina o Gradle 9.2 (suporta até o 25) não compila o `build-logic` ("Unsupported class file major version 71"); 21 é o Java dos mods | Atualizar o Gradle a cada Java novo; voltar ao `apply from` (só esconde o problema) |
| 2026-10-20 | Projeto **`dev/`** (plugin `tc.dev`) com `runClient`/`runServer` de todos os mods TC juntos e os jars de `libs/`; cada mod mantém o próprio `runClient` | Testar a convivência dos mods como no ATM10 sem perder o teste isolado (que abre mais rápido e não mistura erros) | Pôr todos os mods no `runClient` de cada um (todo teste ficaria lento e dependente do MineColonies) |
